# Reviewer Web API

**Kind: Implementation profile**

## Scope

`@slop-lab/dim-web` supplies an optional authenticated operations UI and
Project-scoped human review frontend. It owns browser sessions and a fixed
projection of existing host, CI and Git authority ports. Ordinary Git host
operations require no managed control plane. The backend may configure host
operations, CI query/operator connections, managed reviewer/promoter identities,
and authenticated service-console links independently. It must never expose a
generic command, selectable upstream URL, or credential proxy.

## Trusted startup and identity binding

Startup consumes one absolute, caller-owned, non-symlink, mode-`0600` regular
JSON file. The service accepts only loopback bind addresses and an explicit
public HTTP(S) origin. Plain HTTP is limited to loopback origins for local
verification; production origins use HTTPS.

The file contains scrypt hashes and explicit `read`, `operator`, and `reviewer`
roles for local accounts. There is no singleton reviewer-account alias. Optional
native Git configuration selects a single reviewer identity shared deliberately
by accounts granted the reviewer role. When native Git is selected, before
opening its listener the service calls `GET /v1/human-reviewer-identity`
without redirects. Startup requires role `human-reviewer`, service `native-main`,
and the reviewer ID and generation ID from the private configuration. Every
business request carries that `X-Dim-Generation-Id`. A generation change rejects
existing requests; reconnect and initialize a current configuration before
restarting the web service. Identity attestation does not grant Project access:
the native service independently checks required-reviewer authority for each
review.

`dim-web init CONNECTION --project PROJECT --output CONFIG [--port PORT]`
consumes the private reviewer connection generated by managed control-plane
connect. It verifies the live identity/generation, writes a new mode-0600 config
without overwriting a file, and prints a fresh browser login password. Only its
scrypt hash is stored. `serve CONFIG` consumes that complete private config.

The browser never receives the native username, password, Authorization header,
or a selectable native URL or operation. Configuration reload is not supported;
changing identity or scope requires restart and fresh attestation.

## Browser authentication and request integrity

Local passwords are verified against fixed-parameter scrypt hashes. One
process-global token bucket admits an initial burst of five derivations and
refills one token per second; at most two admitted derivations run concurrently.
The bucket is not keyed by an attacker-controlled account name, admitted work
is never refunded, and excess work is not queued. Either bound returns `429`
with `Retry-After: 1`. Unknown users and known users with a wrong password both
perform one derivation and constant-time hash comparison, and their login
failures are indistinguishable. A successful login creates independent random
session and CSRF tokens held only in process memory and invalidates every prior
session for that account. The session cookie is opaque, `HttpOnly`,
`SameSite=Strict`, path `/`, and `Secure` whenever `publicOrigin` is HTTPS.

Sessions enforce configured idle and absolute deadlines. Expired sessions are
pruned across the store before login and session creation. The store has a hard
256-session cap; a valid login that cannot replace an account's existing
session and cannot obtain capacity receives `429` with `Retry-After: 1`.
Logout deletes the session, process restart deletes all sessions, and an
expired, rotated, deleted, malformed, or unknown cookie receives `401`. Every
unsafe operation, including login and logout, requires the exact configured
`Origin`; authenticated unsafe operations additionally require the current
synchronizer token in `X-DIM-CSRF`. Origin or CSRF mismatch receives `403`
before native dispatch.

`GET /healthz` is the only unauthenticated liveness route and returns no
identity, configuration, or dependency state. Every `/v1` route either creates
an authenticated session or requires one. Responses use `Cache-Control:
no-store`, a deny-all content security policy, no-referrer policy, content-type
nosniff, and framing denial.

## Fixed review surface and browser DTO

The service accepts these native-backed routes:

- `GET /v1/projects/PROJECT/repositories/root/reviews` (at most 100 summaries)

- `GET /v1/projects/PROJECT/repositories/root/reviews/REVIEW_ID`
- `POST /v1/projects/PROJECT/repositories/root/reviews/resolve`
- `POST /v1/projects/PROJECT/repositories/root/reviews/REVIEW_ID/approvals`
- `POST /v1/projects/PROJECT/repositories/root/reviews/REVIEW_ID/revocations`
- `POST /v1/projects/PROJECT/repositories/root/reviews/REVIEW_ID/promotions`

The path Project must equal the configured Project and the repository must be root.
Foreign and malformed paths return `404` without native dispatch. Query strings,
encoded suffixes, unlisted review action suffixes, arbitrary URLs, and arbitrary
methods are absent.

The resolve POST body contains only `proposalRef`, is size-bounded, and is
protected by session, exact Origin, and CSRF checks. It resolves current published
review evidence using the installed service's resolve API, then reads its exact
review ID. Review creation belongs to the control plane.

Both action POSTs accept only an empty JSON object and require the same session,
exact Origin, CSRF, Project, repository, and exact review-ID checks. Before
native dispatch, the session account must have the explicit `reviewer` role;
other authenticated accounts receive `403`. Approval
generates a UUID request ID and delegates to the native human-reviewer route, which revalidates required-reviewer and
stale-evidence authority. Self-revocation first selects only the configured
reviewer ID's active approval from a freshly read exact-review DTO, then delegates
that approval ID to the native revocation route, which independently enforces
ownership. The browser cannot supply an approval ID or select another reviewer.
Each success returns a freshly read review DTO so visible status is the native
result, not an optimistic browser state. In-page review navigation and sign-out
remain locked from mutation dispatch until that DTO is rendered, preventing a
new browser operation from aborting the authoritative result refresh.

The web service has no administrator credential or administrator route. Native
administrator revocation may be exposed only by a future separately configured
and separately attested administrator transport identity; the reviewer credential
must never be widened or reused as administrator authority.

Native review responses are parsed and projected into an explicit browser DTO.
The DTO includes immutable IDs/refs/revisions, printable changed paths and
symlink targets, object IDs and modes, printable patch text, required reviewer
IDs, safe approval/revocation timestamps, and the envelope’s quality revision.
No terminal CI summaries are fabricated. It
also includes the account-specific boolean `canDecide`; read-only authenticated
accounts receive `false` and the browser exposes no decision control. It
omits `patchBytes`, raw path bytes, policy digest, writer username, reviewer
username, revoker username, reporter username, native credentials, and every
unknown native field. Patch and path strings remain untrusted JSON data and
must be rendered as text, never HTML.

## Bounds and verification

Configuration, browser request bodies, native responses, native request time,
HTTP headers, HTTP request time, keep-alive lifetime, and requests per socket
are bounded. Password derivation concurrency and total in-memory sessions are
also bounded. The native client performs no redirect following.

The configured loopback HTTP native transport does not authenticate the native
server as a network peer: the Basic credential authenticates this client to the
process that owns the listener. It is not a shared-host production boundary.
Shared-host deployment requires peer-authenticated TLS or a
permission-protected Unix socket, neither of which this implementation profile
provides.

Paired development tests use an activated installed native bundle, real disposable
Git repositories, and real localhost servers. They cover mode and symlink
configuration rejection; wrong native credentials, role, generation, and reviewer identity; login failure; cookie flags; idle and absolute
expiry; CSRF, Origin, logout replay, foreign Project/repository, tampered path,
and generic proxy denial; published review resolution; generation restart rejection, and omission of native secret
and raw-byte fields. They also cover concurrent and sequential derivation
saturation, one-token refill, recovery, unknown-account equivalent work,
account session rotation, logout after rotation, expired-orphan pruning, and
hard session capacity. They additionally cover required reviewer-account
binding, two-account review DTO and action authorization, read-only control
omission, and delayed mutation responses that cannot be superseded by in-page
navigation before the committed native result is rendered.

## Host and CI operations

`init-operations SETTINGS --output CONFIG` creates a new private configuration
and browser operator login without contacting or loading managed Git/CI.
Reviewer initialization may add `--operations SETTINGS` and `--promoter FILE`.
The optional promoter connection must share the reviewer endpoint/generation;
its distinct `host-promoter` identity is attested before startup.

Authenticated status exposes only configured host IDs, selected capabilities,
configured generation and credential-free console URLs. Host IDs map to trusted
server-side DIM executables and existing host selectors. GET workspace lists
project only immutable ID, name, runtime, phase, observed runtime status and
resource limits. POST workspace actions allow only start, stop, restart,
recreate, discard and resources; each requires `operator` role, Origin/CSRF and
an expected workspace UUID. The adapter invokes the public CLI without a shell;
the core host application verifies the UUID under its lifecycle lock before
mutation. Executable paths, state locations and host selectors cannot come from
the browser. Subprocess time and output are bounded.

CI read endpoints return bounded recent summaries or one execution's diagnostics
using a private generation-bound query connection. Worker occupancy and mutation
use a separate private operator connection. Browser cancellation/retry additionally
requires the operator account role. Cancel does not free running capacity before
owned cleanup; racing success diagnostics do not become published Git evidence.
Retry accepts an explicit UUID request key and returns the same new aggregate on
replay. Only the latest cleaned finished execution may be retried. Webhook intake
identity remains unique, and a newly issued grant replaces the prior latest Git
attempt. No separate browser or operator execution authority exists.

Configured worker occupancy must not be presented as live heartbeat status.
Raw logs remain bounded to the execution service's retained prefixes and
truncation metadata. The service never returns grants, worker leases or credentials.
Backend failures are sanitized. Responses from an earlier browser session cannot
populate a later account's rendered view.

Promotion requires the browser operator role and the separately attested promoter
credential. It does not grant reviewer authority. Native Git remains responsible
for required human decisions, current execution evidence, freshness and protected
ref compare-and-swap. Approval and promotion roles must never be conflated.

Operations and review use separate browser views; opening the optional operations
panel must not push the fixed evidence/review controls below the supported
viewport or weaken existing literal-patch navigation and accessibility behavior.

## Resource priority

Development containers and CI supervisors have positive OOM victim adjustment.
An administrator-installed web system service may set `OOMScoreAdjust=-500`
with explicit memory/CPU/task bounds. An unprivileged user process must not be
assumed able to lower its own OOM score. Deployment does not occur implicitly.
